# 2026-09-26 部署问题与 HUSTOJ 解耦事项

本文记录 syvps 开发测试环境联调中实际遇到的问题、当天完成的修复，以及后续建议。下文“已修复”仅指 syvps 实验部署已验证；相关代码与契约变更保留在 `exp/start`，尚未作为通用修复合入 `main`。本文可独立于修复代码合入。解耦方案和开机自启仍是待办。

## 1. 目标与环境

目标是让教学前端、课程服务与 HUSTOJ 在开发测试环境中连通，能够登录、查看课程、使用题库并接入判题能力。继续复用 HUSTOJ 的账号、题库和判题事实；课程、教学班、选课、题单及教学统计由课程服务管理。产品边界参见 [集成契约](contract-v1.md)。

本机使用 Colima；本次实际部署在 NixOS 主机 syvps，通过 EasyTier 访问。

## 2. 已发现的问题与处理

### 2.1 HUSTOJ 原生身份接口缺失

**现象：** 教学页面提示“`HUSTOJ 身份服务暂时不可用，请重新登录后再试。`”

**原因：** 课程服务依赖 `course.php?mode=session` 验证 HUSTOJ 原生会话，而本次使用的社区镜像没有提供该接口。当前集成对镜像内文件和 PHP 会话实现有隐含依赖。

**已处理：** 实验分支增加 `deploy/hustoj/course.php`，安装到 HUSTOJ 网页根目录。该桥接文件读取原生 PHP 会话，检查用户有效性，返回课程服务需要的身份信息。远端文件位于持久挂载目录 `/srv/hoj-hustoj/data/web/course.php`，本次重启及 Web 容器重建后仍存在。

**验证：** PHP 语法检查通过；无会话请求返回 401；有效测试会话可通过课程 API 获取身份并进入学生页面；退出后再次访问身份接口返回 401。

**后续：** 把接口安装、版本和健康检查纳入部署流程，避免依赖人工向运行中的站点补文件。

### 2.2 站点名与容器环境变量不一致

**现象：** HUSTOJ 退出登录曾返回 500。修正运行配置后，主机重启又将站点名恢复为带空格的 `HOJ Dev`。

**原因：** 站点名参与 HUSTOJ 会话相关行为，带空格的配置引发异常。磁盘 `.env` 已设为 `HUSTOJ_NAME=HOJ-Dev`，但旧容器创建时保存的环境变量仍为 `HOJ Dev`；重启容器会继续使用旧值，并重新写入 PHP 配置。

**已处理：** 使用现有 Compose 配置重建 Web 容器，使容器环境变量与 `.env` 一致。当前 `HUSTOJ_NAME` 和 PHP 配置中的 `OJ_NAME` 均为 `HOJ-Dev`。

**验证：** HUSTOJ 首页返回 200；`/oj/logout.php` 返回正常的 302 跳转；身份桥接文件保留且匿名请求返回 401。

**后续：** 部署流程应校验会话相关配置，并明确环境变量修改后需要重建容器。单纯重启不能应用新的 Compose 环境变量。

### 2.3 跨库查询的字符排序规则冲突

**现象：** 教学班排行榜请求 `/api/ranklist?offeringId=1` 返回 503，页面显示“`数据库操作失败，请查看课程服务配置与授权`”。登录、课程列表和学生侧教学班详情仍可正常访问。

**实际数据库错误：**

```text
ERROR 1267 (HY000): Illegal mix of collations
(utf8mb4_uca1400_ai_ci,IMPLICIT) and (utf8mb4_general_ci,IMPLICIT)
for operation '='
```

`codemind_course.cm_enrollment.user_id` 等课程字段使用 `utf8mb4_general_ci`；本次 HUSTOJ 的 `jol.users.user_id`、`jol.users.nick` 等字段使用 `utf8mb4_uca1400_ai_ci`。查询直接跨库比较两个字符串字段时失败。连接凭据及该查询所需授权正常。

旧契约基于 MariaDB 10.6 环境，假定 `jol` 的排序规则也是 `utf8mb4_general_ci`。此次部署说明该假设不能作为不同 HUSTOJ 镜像和数据库版本之间的固定契约。

**已处理：** 在 [service.py](../service.py) 的三处跨库用户关联中显式指定 `COLLATE utf8mb4_general_ci`，同时处理昵称与课程用户 ID 的 `COALESCE` 表达式：

- 教学班排行榜。
- 教师侧教学班详情中的学生统计。
- 教师侧学生列表。

代码已同步到 syvps 并重启课程 API。实验分支同步调整了 `schema/001_cm_course.sql` 的说明及集成契约，不再假定所有 HUSTOJ 部署都使用同一种排序规则；这些调整随修复代码保留，主线契约尚未变更。

**验证：** 通过 5555 入口使用学生、教师测试账号请求教学班排行榜、全站排行榜、教师教学班详情和学生列表，均返回 200。此次验收覆盖上述读取路径；本轮修复没有重新验证完整提交与判题链路。

**剩余问题：** 显式 `COLLATE` 解决了当前兼容错误，业务查询仍直接依赖 HUSTOJ 表结构。其他镜像或数据库组合仍需兼容性验证。

**合入前需确认的兼容性：** 显式排序规则会决定字符串比较语义，可能改变其他部署对用户 ID 等值匹配的假设，也可能影响索引使用和查询性能。PHP 身份桥接依赖当前镜像的初始化、会话键及用户查询行为，不能直接覆盖其他 HUSTOJ 改造版已有的 `course.php`。当前验证只证明 syvps 上相关路径恢复，尚不足以证明这些修改适用于所有用户环境。通用修复需要先明确支持的 HUSTOJ、PHP 和数据库组合，再验证身份映射、查询结果与性能。

### 2.4 课程服务与入口没有开机自启

**现象：** 主机重启后 HUSTOJ 三个容器自动恢复，教学前端、课程 API 和 5555 入口消失。

**原因：** 前端和 API 使用 tmux 启动，5555 使用临时 systemd socket，EasyTier 防火墙放行规则也是运行时添加。这些配置尚未纳入 NixOS 声明式配置。

**已处理：** 当天重新启动前端、API、5555 socket 和防火墙规则，从本机经 EasyTier 请求入口返回 200。

**状态：待持久化。** 目前下一次主机重启仍需重新启动上述组件。需要在 `~/my-vps-config` 中固化 systemd 服务、socket 和接口范围内的防火墙规则，并验证启动顺序与故障重启。该配置目录存在其他未提交的系统配置变更，部署时需明确本次生效的配置范围。

## 3. 解耦方向

本次问题表明，教学业务已依赖 HUSTOJ 的 PHP 会话行为、部署文件位置、数据库字段与排序规则。应将这些依赖集中到明确、可测试的接口边界，继续复用 HUSTOJ 的现有能力。

建议的调用关系：

```text
教学前端 → 课程服务 → HUSTOJ 适配层 → HUSTOJ
              ↓
            课程库
```

### 第一阶段：集中 HUSTOJ 访问

把分散在 `service.py` 中的原生会话验证、用户资料读取、题目读取、提交创建和判题结果读取移入适配模块。第一阶段可继续使用当前 SQL 和 PHP 桥接方式，先建立模块边界。

适配层向课程业务返回稳定的数据结构，集中处理表名、排序规则、HUSTOJ 状态码以及上游故障。课程权限仍由课程服务根据任课和选课关系判断。

验收要求：

- 教学业务通过适配接口访问 HUSTOJ；相关 SQL 和会话协议集中管理。
- 当前环境及原有兼容环境中的登录、用户资料、题目、提交和结果查询满足同一接口契约。
- 适配层故障能够定位到身份、用户、题目或判题能力，而不是统一表现为不明原因的数据库错误。

### 第二阶段：移除教学查询中的跨库 JOIN

优先处理本次受影响的排行榜、学生列表和教学班统计。课程服务从课程库读取学生与提交归属，再通过适配层批量读取昵称、判题结果等数据，完成业务聚合。

实现时需保留现有排序、分页、统计口径和权限行为，避免逐条远程查询导致性能下降。数据量增长后，可评估将展示资料与判题结果同步到课程侧统计表；同步方案需明确延迟、重判更新和对账方式。HUSTOJ 继续作为判题事实来源。

### 第三阶段：建立有版本的服务接口

待适配接口稳定后，评估由 HUSTOJ 一侧提供身份、题目、提交与判题结果接口，使课程服务能够通过网络协议访问这些能力。

这一阶段需要定义提交去重、超时后的状态确认、重试、结果同步和接口版本兼容。不能简单把一次数据库写入替换成一次 HTTP 请求后就认定解耦完成。

## 4. 建议推进顺序

| 顺序 | 待办 | 完成标准 |
|---|---|---|
| 1 | 建立 HUSTOJ 适配模块 | 集中身份、用户、题目、提交和结果访问，业务使用稳定接口 |
| 2 | 拆除三处跨库用户关联 | 排行榜、教师统计、学生列表保持既有结果与权限行为，覆盖分页与排序 |
| 3 | 完善故障诊断 | 服务端记录可定位的错误类别和数据库错误码，避免记录密码、Cookie 等凭据 |
| 4 | 评估服务接口与统计同步 | 明确契约、兼容范围、提交去重及对账方式后再实施 |

开机自启属于部署生命周期问题，可独立于应用解耦推进。本文记录的 `COLLATE` 与身份桥接修复已落地；适配模块、跨库查询拆分及服务接口建设尚未实施。
